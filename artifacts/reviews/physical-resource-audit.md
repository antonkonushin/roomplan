# Read-only physical-render resource audit — 2026-10-16

Requested by visual builder while the lead controls the browser. No browser operations or production changes were made. This is a source/resource-lifetime review, not a reproduced diagnosis of the all-zero render target or later lost WebGL context.

Current `cloneForTracing` clones mesh geometry/materials and duplicates canvas/typed-array texture sources. It restores the original Source version after `Texture.clone`, whose implementation shares Source. No direct disposal of the original mesh geometries or material instances was found in the inspected current cleanup. Texture formats with array/video/compressed/custom sources are outside the currently exercised canvas fixture; this is not a universal asset-isolation proof.

Two concrete remaining resource-lifetime risks:

1. **Dedicated contexts are created per attempt but not explicitly released.** `renderPhysical` constructs a new detached-canvas `WebGLRenderer` each time, then calls `renderer.dispose()` without explicit context loss. Context lifecycle therefore depends on garbage collection/browser policy. Repeated probes can consume the browser's limited active-context budget even if application-owned GPU resources are disposed. This is a plausible contributor to later context-creation failure, not a demonstrated cause. Reuse a persistent private renderer or explicitly release only the private renderer context after cleanup; never release `room.renderer`.
2. **Fullscreen geometry is shared beyond final cleanup.** Vendored `Pass.js` creates one module-level `_geometry`; every `FullScreenQuad` uses it and `.dispose()` disposes that geometry. A headless direct test with two real FullScreenQuad instances confirms `sameGeometry=true` and disposal of one raises a disposal event on the other's geometry. The tracer's `RenderTarget2DArray.setTextures()` calls `setSize()` on dimensions/depth change; the target's overridden `dispose()` calls its `fsQuad.dispose()`. Thus bypassing subclass disposal only in `renderPhysical`'s final cleanup does not remove the earlier allocation/resize path. This may trigger editor fullscreen-resource invalidation across renderer instances. It is not, by itself, proof of permanent black rendering: Three may recreate buffers. For strict isolation, give offline quad instances their own geometry or prevent their ownership cleanup from disposing the shared singleton.

The vendored `WebGLPathTracer.dispose()` references `_renderQuad` while its constructor uses `_quad`; calling that library method blindly is unsafe in this pinned source. Current application cleanup uses `_quad` explicitly, which avoids that mismatch. Its handwritten cleanup should nonetheless keep editor-control restoration in an unconditional nested `finally`, so a future cleanup exception cannot leave recording/controls locked.

The output-statistics guards now reject zero/transparent targets and withhold a fake success PNG. Retest needs actual nonempty pixels, correct editor materials and successful interaction after both success and failure, then a second physical attempt. Do not infer a rendered-image fix from disposal changes alone. Earlier `round5-physical-interior.png` remains a failed fully transparent output.
